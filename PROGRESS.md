Launches the *system* Chrome binary (`CHROME_EXECUTABLE_PATH`, defaults to `/usr/bin/google-chrome` in dev) directly rather than downloading Playwright's own bundled Chromium — user-approved explicitly (see Deviations). - Deployment target (v0.3 §3.6): —

- No git: `lore-core/` is intentionally not a git repo yet, per explicit user instruction ("for now").
- Local dev database: PostgreSQL 16 installed via `apt` (user ran with sudo) on this machine, auto-starts via systemd. Role `lore_core` / database `lore` created for local dev (`sudo -u postgres psql`, one-time setup, user ran it). `DATABASE_URL` lives in `lore-core/.env` (not `.env.example`, which keeps placeholders only) — local-only dev password, not a real secret, but still not meant to be committed once git is set up.
- AI providers: hand-rolled adapters (Gemini/Groq/OpenRouter SDKs already installed in `agentic_env`), not `litellm` (not installed — v0.3 §2.1/§2.5 explicitly allows either). `AI_PROVIDER_KEYS`'s internal format (CP-0 only reserved the env var name) is a JSON object: `{"gemini": "...", "groq": "...", "openrouter": "..."}`, parsed in `app/ai/gateway.py::_parse_provider_keys`.
- **Ownership-scope convention (CP-17, v0.2 §6.7's RLS matrix, v1.0 §1 item 1), locked in going forward: every service-layer function that receives a foreign id (a path param or a request-body id naming a row it didn't just create) must re-fetch that row and check its owner/member column against the caller's `profile.id` before acting on or returning it — never trust that an id reaching a service function was already validated by something upstream.** This is the whole substitute for RLS in this architecture; there is no policy engine catching a missed filter. CP-17's own audit (grepped every `session.get`/`select` call site in `app/services/*.py`, ~75 total) found this convention already held everywhere without exception — logged here as the enforcement mechanism v1.0's own CP-17 step 3 asks for ("a lint rule or code-review checklist item") since no custom ruff/AST plugin was written for it (out of proportion for a solo-dev build): any future service function taking a foreign id must follow this same pattern, and `app/tests/test_idor_suite.py` is where its own negative-path test belongs.

## Deviations from the PDR
- 2026-09-09 — CP-0 — Pinned `PyJWT` instead of the spec-named `python-jose` for JWT handling (CP-3 will use it). `PyJWT` was already installed in `agentic_env` and serves the identical purpose; avoids adding a redundant JWT library. Functional contract (validate Supabase-issued JWTs) is unchanged.
- 2026-09-09 — CP-0 — Added `asyncpg` to the dependency list even though v1.0's CP-0 step 5 doesn't name it explicitly: `sqlalchemy[asyncio]` requires an async driver to actually connect to Postgres, and asyncpg is the standard one. Necessary omission-fill, not a design change.
- 2026-09-09 — CP-1 — Reused the old `lore-pack/supabase/migrations/0001_init.sql` (the "full DDL" v0.2 §6.2 itself references) as the exact field-type/constraint source, then adapted the *ownership model* only, as CP-1 instructs: dropped `enable row level security` + all RLS policies; dropped the `auth.users` FK on `profiles.id` (no local Supabase-Postgres integration in this standalone-auth architecture, PDR v0.3 §2.3 — `profiles.id` is populated from the JWT `sub` claim in CP-3/CP-6, not server-generated); dropped every `SECURITY DEFINER` SQL function (`award_completion`, `apply_xp`, `join_party`, `leave_party`, `party_checkin`, `mint_share_token`, `resolve_share_token`, `claim_recap_jobs`, `finish_recap_job`, `handle_new_user`, `is_party_member`, `is_party_lead`) and the `on_auth_user_created` trigger — these are exactly the game-math/authorization logic that CP-3/CP-6/CP-8/CP-9/CP-10/CP-11 rebuild as Python service modules; dropped Postgres role grants/revokes (`authenticated`/`service_role`/`anon` are Supabase/PostgREST concepts, irrelevant once the Python service is the sole DB client with its own credentials).
- 2026-09-09 — CP-1 — Did not create a `party_quest_pool` table (present in the old v0.2 DDL as a seed/reference table). CP-1's own explicit table-to-model-file mapping doesn't list it, and v0.2 §6.2's summary table doesn't mention it either — it only shows up via Appendix F §F.3 content. Following CP-1's literal instruction ("do not invent an alternate layout") over the older DDL; the curated party-quest-pool content will most likely become a Python constants module (matching how CP-7 handles the 24 fallback classes) when CP-10 gets there — deferring that call to CP-10 rather than deciding it now.
- 2026-09-09 — CP-1 — All surrogate UUID primary keys are generated Python-side (`uuid.uuid4()` at the ORM layer) instead of the old DDL's `gen_random_uuid()` DB-side default. Consequence: the `pgcrypto` extension isn't needed at all. This mirrors the same reasoning as the `referral_code`/`invite_code` short-code generation below (Python-side, not DB-side) and is a natural, low-risk consequence of the service layer owning all writes.
- 2026-09-09 — CP-1 — `referral_code` (profiles) and `invite_code` (parties) are generated by a Python helper (`app/db/base.py::generate_short_code`, `secrets.token_hex(4)`) at insert time, replacing the old DDL's bespoke `short_code()` SQL function. Same output shape (8 hex chars), just generated in the layer that now owns business logic.
- 2026-09-09 — CP-1 — Added `created_at` (and, where the table is genuinely mutable, `updated_at`) to `notification_prefs`, `entitlements`, `moderation_flags`, `ai_usage`, and `app_flags` — the old v0.2 DDL omitted these on a few tables, but CP-1's own general rule ("every table gets created_at; mutable tables get updated_at") is the more specific, current instruction, so it takes precedence. No column names or business meaning changed, just filling a gap between the reference DDL (predates this rule) and CP-1's explicit text.
- 2026-09-09 — CP-2 — `AppFlag.value` (CP-1 model, `app/db/models/platform.py`) widened from `Mapped[dict]` to `Mapped[Any]`. - 2026-09-09 — CP-7 — **The most consequential finding of this checkpoint.** Appendix E states quiz scoring is "base stats = 1 each + points, then normalized to sum 15 (cap 5, floor 1; overflow redistributes to the lowest stat)" — but that rule alone never reaches 15. ## Bugs found and fixed while verifying CP-9 against a real database
- **Real bug in `app/services/recaps.py::process_recap_job`'s own retry/poison path.** The `except` block called `await session.rollback()` (to discard any partial state from the failed generation attempt) and then immediately did `job.attempts += 1` — but `rollback()` expires every attribute SQLAlchemy loaded on `job`, so that plain attribute read triggers an implicit lazy-reload. ## Bugs found and fixed while verifying CP-12 against a real database
- **Real bug in `app/services/notifications.py::send_notification` — the most consequential one this build has found in a while, since it would have silently broken FR-8.2 in production.** The function's final lines were `if channel_sent is None: return False` followed only *afterward* by `session.add(NotificationLog(...)); await session.commit()`. But `_dispatch_push` (called earlier in the same function) can mutate `PushSubscription` rows — bumping `failed_count`, or deleting a row outright on an explicit dead-token response — *independently* of whether the send as a whole ultimately "succeeded." Whenever every attempted channel failed (`channel_sent` stayed `None`), the function returned before ever reaching `commit()`, and `AsyncSession`'s default behavior on a context-manager exit with no explicit commit is to roll back any pending work — silently discarding every one of those subscription mutations. Worth remembering: a function that does multiple related things (dispatch attempts *and* bookkeeping mutations as a side effect) must commit unconditionally on every exit path, not just the "happy" one — an early return guarding only the *primary* result can silently roll back *secondary* state changes nobody was guarding.
